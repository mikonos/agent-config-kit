# D6 承重假设清单 · 标准表模板

> 给所有 research tool（Tool 1/3/3b/6/7/8 等）收尾时强制使用的统一 D6 表头。
> 真源规则见 `SKILL.md` § D6（Load-Bearing Assumption Failure Map）和 Rule 14。
> 表是 D6 的**唯一**呈现形式——不再允许散写式表述（"某条假设可能影响 …"）。

---

## 1. 标准表头（强制）

每个 tool 收尾的「承重假设清单」必须使用以下表头，列名、列顺序、字段含义都不许改：

```markdown
| ID | 假设 | 证据等级 | 失效后果（人话） | 建议验证方式（Tool 9/10 交接） |
```

### 字段定义

- **ID**：本工具内编号，前缀 `LB-`（Load-Bearing），如 `LB-1`、`LB-2`。跨工具引用时加 tool 前缀，如 Tool 6 的 LB-3 在台账里写 `T6-LB-3`。
- **假设**：一句话写明用户行为/心理/能力/市场动力的具体主张；必须可被推翻，不写「用户大概会喜欢」这种空话。
- **证据等级**：四档（与 `00_证据可信度台账_{product}.md` 口径一致）：
  - **A**：一手访谈实证（≥3 户 G3+G4 真实切换事件）
  - **B**：二手数据（评论挖掘、行业报告、平台运营数据）
  - **C**：方法论推断（专家视角 + 跨案例类比，无本产品直接证据）
  - **H**：[HYPOTHESIS]，纯假设
- **失效后果（人话）**：必须三段——「若 X 被推翻 → Y 抓手作废 + Z 营销/路线图后果」；不许写「Tool 7 §4 整段重写」这种内部黑话；必须能让不熟项目的读者立即明白「啊这件事就不能做了」。
- **建议验证方式（Tool 9/10 交接）**：必须能直接喂给：
  - Tool 9 访谈题（switching event / probe tree / 听某种心智 slicing）
  - Tool 10 问卷题（importance×satisfaction / Van Westendorp / 行为频率）
  - 工程预研 / 法务 audit（Rule 18 能力体检类）

不写「之后验证」「待 Tool 9/10」——必须具体到「N 户 G3 妈妈访谈某具体场景，验证她的真实 trigger 是否如假设所述」。

## 2. 完整示例（Tool 6 风格）

```markdown
## §X. 承重假设清单（D6）

| ID | 假设 | 证据等级 | 失效后果（人话） | 建议验证方式（Tool 9/10 交接） |
|---|---|---|---|---|
| LB-1 | G3 妈妈在「孩子开学第一周」会主动 hire 一个家庭 AI 中心（big-hire trigger 真实存在） | H | 若错 → G3 不是 Tool 4 §3 圈定的靶心；Tool 7 §4 P0-1/2/3 优先级整体降级；营销台账 Q3 back-to-school campaign 投放计划作废 | Tool 9 套餐 A 切换访谈 8 户 G3 妈妈，问她「上一次主动想找一个能帮你记/想/协调的东西，是哪一天，触发是什么」 |
| LB-2 | G3 妈妈愿意把家庭日历 / 家庭消息群 / 学校邮件交给一个本地 AI 设备处理（隐私心智门槛可越过） | C | 若错 → Tool 8 Data In 信息源集成只剩 Google Calendar 一项；多数 P0 功能（自动消息分拣 / 接送提醒 / 礼物购买跟单）失去数据基础；hero「the home keeps track」无承诺力 | Tool 9 套餐 C 隐私访谈 6 户 G3，递给纸版 data lifecycle 卡片让她说哪条她接受 / 哪条不接受 + Tool 10 隐私意愿 5 点量表 N=200 |
| LB-3 | AI 模型在「家庭消息批量分拣」任务上 ≥85% 准确率，且错分类不出现在「孩子安全 / 医疗 / 学校紧急」类目下 | H | 若错 → Tool 7 P0-5 自动消息分拣抓手作废；hero「never miss a beat」承诺降级；档 2「设备替你想好你同意才执行」必须改成档 1「设备只列选项你自己挑」 | 工程预研：用 1000 条真实家庭群消息样本批量测试现成模型；同时跑 Rule 18 能力体检（in principle / in practice / 距可用还差什么） |
```

## 3. 与 D5 营销台账 / Tool 9-10 的接口

- 每个 tool 写完 D6 清单后，**必须**在 Phase 3 close / Phase 7 audit 前把承重假设 ID 复制进 `上市与营销信号台账_{product}.md` 的「承重假设跟踪」段落（如台账没有该段，append 一段空段并指向各 tool 的 D6 表）。
- Tool 9 设计访谈题时，按承重假设 ID 倒推 probe tree；Tool 10 设计问卷时，按承重假设 ID 选 importance×satisfaction 题。
- 承重假设的「证据等级」与 `00_证据可信度台账` 必须同步——证据升级（H → C → B → A）由实际证据获得驱动，不能凭判断升档。

---

## 4. 与普通 [HYPOTHESIS] 标签的区别

- 普通 `[HYPOTHESIS]` 标签：标在主稿任何不确定的判断上，免责声明性质。
- **承重假设**（D6 收尾）：拿掉这条假设、下游某个具体动作就不成立——必须进 D6 表。
- **判定测试**：拿掉这条假设，下游某条抓手 / 营销硬规则 / 路线图条目还成不成立？不成立 = 承重。

不强制每个 [HYPOTHESIS] 都做 D6；只承重的做。

---

## 5. 计数与漂移防呆（Rule 15）

- D6 表是承重假设的**唯一计数真源**——主稿 §0 速查 / 章节标题 / 上下游台账提到「N 条承重假设」时必须对得上 D6 表实际行数。
- 任何往 D6 表增删条目的动作，必须同步当场更新：① 本节表头 ② 主稿速查 ③ 营销台账承重假设跟踪段 ④ 证据台账 ⑤ quality_audit 报告。
- 漏同步 = D5 状态冲突 = Rule 11 cascade 失败，blocked 进 Phase 7.5 expert panel review。

---

## 6. 与 Rule 18 能力体检的关系

- D6 管承重「需求 / 行为 / 心理 / 市场假设」的失效后果——是「用户会不会这样做」的事。
- Rule 18 管承重「技术能力」的当下成熟度——是「设备/模型/API 能不能做到」的事。
- 两表互补，不重复。同一项「AI 准确率」相关假设：行为侧（用户愿不愿意把这个任务交给 AI）进 D6；能力侧（AI 在这任务理论上限/眼下实际多少）进 Rule 18 能力体检。
