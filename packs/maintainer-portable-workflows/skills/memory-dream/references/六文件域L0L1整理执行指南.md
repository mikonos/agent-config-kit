# L1 六文件域：大块正文 → 原子卡 → 双索引（MEMORY + L1）

> **你要的流程**：把**原来那份大的 feedback 内容**（或等价的长段落）**拆成**多张根目录 **`memory/YYYYMMDD_feedback_*.md` 记忆原子**，再**挂索引**到 **`MEMORY.md`**（L0 对应域小节）与 **`memory/topics/<id>/feedback.md`**（`## 原子卡索引（memory-dream 维护）`）。  
> **真源体例**：根目录 `MEMORY.md` 顶部（Obsidian `- [[路径.md]]：hook`，**不写** `|` 显示别名）；与本文冲突时以 `MEMORY.md` 为准。  
> **模板与字段清单**：`references/cc-feedback-atom-examples-and-template.md`（Phase 3 勾选表 + YAML 模板）。

---

## 0. 「大块」可能长什么样

| 来源 | 说明 |
|------|------|
| **L1 内过长段落** | `feedback.md` 里「范式级」下多条 **确认/纠正**，每条已像一条规则，但仍堆在同一文件。 |
| **一次性搬运稿** | 例如 `05_每日记录/…/CC记忆参考_本机搬运/` 下整段 feedback 真源，尚未落成根目录原子。 |
| **会话里长列表** | 某次对话总结的「用户偏好」列表，准备入库为可检索原子。 |

**目标**：每条**独立可理解、可单独进上下文的主张** → **一张原子卡**；L1 只保留范式叙述 + **索引列表**，避免「L1 与原子卡双份真源」长期并存。

---

## 1. 拆分原则（拆什么、不拆什么）

| 原则 | 做法 |
|------|------|
| **一卡一命题** | 一张原子只讲清一件事（一条规则、一条纠正、一条确认）。可对照 `note-split` / 卢曼原子化。 |
| **类型一致** | 纠正与确认 Agent 行为 → `type: feedback`；若其实是稳定画像或项目事实，应改 `user` / `project` 等，见 `cc-vs-zk-memory-mapping.md`。 |
| **命名** | `memory/YYYYMMDD_feedback_<简短英文或拼音slug>.md`；与 `YYYY-MM-DD` **日报**区分；日期取拆分落盘日或与内容事件日一致（团队内统一即可）。 |
| **正文结构** | 对齐 CC：`name` / `description` / `type` + 正文 **`**Why:**`** / **`**How to apply:**`**（详见 `cc-feedback-atom-examples-and-template.md`）。 |

## 2. 执行流程（按顺序做）

### Phase 1 — 切块与草拟文件名

1. 通读大块正文，按 **主题边界** 画断点（一条规则 = 一卡）。
2. 为每块拟定：`YYYYMMDD_feedback_xxx.md` 与 `name` / `description`（`description` 将用于 L0/L1 的 **hook**）。
3. **禁止**：把 `05_每日记录/…/CC记忆参考_本机搬运/` 里**只读示例**直接改写；应**复制模板**到 `memory/` 根目录新文件（见模板文档）。

### Phase 2 — 落盘原子文件

1. 在仓库根 `memory/` 下新建 `YYYYMMDD_feedback_*.md`（每个主题一个文件）。
2. 写入 frontmatter 与 **Why / How to apply**；长案例只给 Vault 内 `[[链接]]`，不把整篇笔记贴进原子。

### Phase 3 — 双索引（核心）

同一批新原子，**每一处**都要出现**相同语义的一行指针**（hook 与 `description` 对齐，可略压缩）：

1. **`MEMORY.md`** → 找到 `## 行为偏好（feedback）→ [[…/feedback.md]]` 小节，在节内**追加**（勿另开重复 meta 句）：
   ```markdown
   - [[memory/YYYYMMDD_feedback_xxx.md]]：一句要点
   ```
2. **`memory/topics/<machine-id>/feedback.md`** → 在 **`## 原子卡索引（memory-dream 维护）`** 下**追加**同构一行（与 L0 **同一套**路径 + 冒号 + 要点）：
   ```markdown
   - [[memory/YYYYMMDD_feedback_xxx.md]]：一句要点
   ```

**自动化**：若该原子来自 **session-summary 抽取轨**，`_session-summary-worker.js` 会在写 `MEMORY.md` 时**同步**追加对应 L1「原子卡索引」行；手工拆分时需**自己双写**或跑完抽取后再核对。

### Phase 4 — 收敛母本（避免双真源）

1. 大段原文若已在 `feedback.md`：将已拆条目改为 **一条 wikilink** 指向新原子，或删去重复陈述，只留「范式级」里仍需并列对照的上下文。
2. 若大块仅在搬运目录：在 `feedback.md` **范式级** 加一句总述 + 指向下列原子索引即可，不必再复制全文。

### Phase 5 — 验收

- [ ] 每个新主题有**且仅有**一个 `memory/YYYYMMDD_feedback_*.md`。
- [ ] `MEMORY.md` 行为偏好节 + `feedback.md` 原子卡索引 **行数一致、hook 一致**（允许 L1 略短）。
- [ ] frontmatter `type: feedback` 与文件名 `_feedback_` 段一致。
- [ ] `05_每日记录/…` 只读示例未被覆盖；禁止内容写进 How 的仍遵守 `core-ops`。

## 3. 其它五类域（类推）

以下类型把上文中的 `feedback` / `行为偏好` / `_feedback_` 换成对应列即可；**拆分 → 根目录原子 → MEMORY 对应节 + 当前 L1「原子卡索引」** 流程相同。

| `type` | L0 小节（示意） | L1 文件 | 原子文件名段 |
|--------|-----------------|---------|----------------|
| `user` | 用户与协作（user） | `user.md` | `YYYYMMDD_user_*.md` |
| `project` | 项目上下文（project） | `project.md` | `YYYYMMDD_project_*.md` |
| `reference` | 运维与工具（reference） | `reference.md` | `YYYYMMDD_reference_*.md` |
| `affect` | 情绪与协作节奏（affect） | `affect.md` | `YYYYMMDD_affect_*.md` |
| `vault` | 知识库状态（vault） | `vault.md` | `YYYYMMDD_vault_*.md` |

**尚无根目录原子时**：L1 里「原子卡索引」可为空或仅注释说明（参见当前 `affect.md` 做法）。

## 4. 附录：导航卫生（可选，与「拆分原子」可分批做）

| 事项 | 做法 |
|------|------|
| 去掉多余 `memory/README.md` | 删除后 `rg 'memory/README'` 清链；索引只靠 L0 + L1 + 命名约定。 |
| 删 L0 冗余 meta 行 | 节标题已 `→ [[…/feedback.md]]` 时，不再加「正文见…」整句。 |
| 历史行格式混排 | 统一为 `- [[memory/…完整路径.md]]：要点`（与 worker 去重一致）。 |
