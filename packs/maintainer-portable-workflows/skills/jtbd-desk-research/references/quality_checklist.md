# JTBD 桌面研究质量审查清单

> 基于 Bob Moesta 的 JTBD 方法论和本次 product 门厅镜研究的经验总结

---

## Phase 0: 研究设计审查

### 执行计划完整性
- [ ] 产品假设清晰（一句话能说明白）
- [ ] JTBD 假设明确（J1/J2/J3/J4 用 Job Story 格式）
- [ ] 研究问题具体（5-7 个可回答的问题）
- [ ] 数据源覆盖全面（Reddit + Amazon + 论坛 + App Store + YouTube）
- [ ] 批次优先级明确（Must/Should/Nice to have）
- [ ] 时间箱合理（2 天采集 + 1 天分析）
- [ ] 最低完成线清晰（时间不足时的保底目标）

### 提取框架规范性
- [ ] 引用格式统一（来源/URL/原文/Job 标签/四力标签/信号类型/强度信号/备注）
- [ ] 四力识别指引明确（关键词/句式）
- [ ] 信号类型定义清晰（6 种类型）
- [ ] 质量控制原则完整（8 条原则）

---

## Phase 1: 数据采集审查

### 数量与覆盖度
- [ ] 总引用数 ≥50 条（必做 Batch 完成后）
- [ ] Reddit 引用 ≥20 条
- [ ] Amazon 引用 ≥15 条
- [ ] 论坛/社区引用 ≥10 条
- [ ] 每个 Batch 覆盖 ≥3 种不同来源/子版块

### 引用质量
- [ ] 每条引用有完整原文（不截断语意）
- [ ] 每条引用有 URL（如可获取）
- [ ] 每条引用有 Job 标签（J1/J2/J3/J4）
- [ ] 每条引用有四力标签（Push/Pull/Anxiety/Habit）
- [ ] 每条引用有信号类型（6 种之一）
- [ ] 高强度信号已标注（点赞数/评论数）

### 样本平衡性
- [ ] 反证样本占比 15-30%（不认同问题、满意现状、质疑方案）
- [ ] 包含成功案例（雇用后满意的）
- [ ] 包含失败案例（解雇/放弃的）
- [ ] 包含高频痛点（多次出现的）
- [ ] 包含情感强烈表达（love/hate/saved my life）

---

## Phase 2: Job Story 验证审查

### 验证严谨性
- [ ] 每个 Job 有明确的验证状态（强验证/弱验证/未验证/反证）
- [ ] 强验证的 Job 有 ≥5 条支撑引用
- [ ] 弱验证的 Job 有 3-4 条支撑引用
- [ ] 未验证的 Job 诚实标注（不强行验证）
- [ ] 反证的 Job 有具体反例

### Job Story 质量
- [ ] 格式符合标准：When [situation], I want to [motivation], so I can [outcome]
- [ ] 代表原话是用户原文（不是改写）
- [ ] 修正/补充基于数据（不是推测）
- [ ] 识别出隐性 Job（用户没明说但行为暗示的）

### Job Statement 质量
- [ ] Phase 2 前已抽取 Job Statement 九格，而不是从引用直接跳产品机会
- [ ] 每条含 `Context / Main Job / Desired Outcome / Compensation Behavior / Current Solution / Verbatim`
- [ ] `Desired Outcome` 可衡量；无法衡量的已标 `待追问`
- [ ] `Compensation Behavior` 是已发生动作，不是“希望产品能...”
- [ ] 每条只对应一个场景切片，没有混入多个 moment
- [ ] 痛点写出情绪和后果，不只是现象描述
- [ ] 每条标 `evidence_grade A/B/C/H`，C/H 不进入需求卡或强产品判断

---

## Phase 3: 四力分析审查

### 四力完整性
- [ ] Push（推力）有 ≥5 条代表原话
- [ ] Pull（拉力）有 ≥5 条代表原话
- [ ] Anxiety（焦虑）有 ≥5 条代表原话
- [ ] Habit（习惯）有 ≥5 条代表原话

### 四力强度对比
- [ ] Push 和 Pull 的强度可对比（哪个更强？）
- [ ] Anxiety 和 Habit 的阻力可量化（多大阻力？）
- [ ] 四力强度对比有明确结论（如：Push + Pull > Anxiety + Habit → 市场机会成立）

### 原话质量
- [ ] 原话是用户原文（不是总结）
- [ ] 原话有情感强度（frustrated/love/hate）
- [ ] 原话有具体场景（不是泛泛而谈）

---

## Phase 4: Workaround 目录审查

### Workaround 完整性
- [ ] 列出 ≥5 种 workaround
- [ ] 每种 workaround 有描述
- [ ] 每种 workaround 有信号强度（引用数）
- [ ] 每种 workaround 有失败原因（用户原话或明确归纳）

### 竞争地图清晰性
- [ ] 识别出直接竞争（同类产品）
- [ ] 识别出间接竞争（替代方案）
- [ ] 识别出非消费（什么都不用）
- [ ] 明确真正的竞争对手（不只是同类产品）

---

## Phase 5: 雇用/解雇时刻审查

### 雇用时刻
- [ ] 有 ≥3 个具体的雇用时刻案例
- [ ] 每个案例有触发事件（什么发生了？）
- [ ] 每个案例有时间线（从想法到行动隔了多久？）
- [ ] 每个案例有决策理由（为什么那天决定行动？）

### 解雇时刻
- [ ] 有 ≥3 个具体的解雇时刻案例
- [ ] 每个案例有放弃原因（为什么不用了？）
- [ ] 每个案例有时间线（用了多久才放弃？）
- [ ] 每个案例有最后一根稻草（什么事件是临界点？）

### 切换时间线
- [ ] 有完整的切换时间线（旧方案 → 第一次想法 → 被动寻找 → 主动寻找 → 决定购买 → 首次使用 → 持续使用/放弃）
- [ ] 每个阶段有时间跨度
- [ ] 每个阶段有关键问题（什么痛点？什么触发？看了什么？担心什么？为何现在？是否满意？为何留/走？）

---

## Phase 6: 产品启示审查

### 启示质量
- [ ] 有 8-10 条产品启示
- [ ] 每条启示基于数据（不是推测）
- [ ] 每条启示可执行（不是泛泛而谈）
- [ ] 启示覆盖：核心价值主张、关键特性优先级、避免的陷阱、设计原则

### 核心洞察
- [ ] 识别出核心差异化（如：被动可见性）
- [ ] 识别出关键场景（如：门厅/出口）
- [ ] 识别出设计约束（如：可靠性 > 功能性）
- [ ] 识别出情感价值（如：心理负荷转移）

---

## Phase 7: 关键引用精选审查

### 精选质量
- [ ] 精选引用 30-50 条
- [ ] 按 Job 分类清晰（J1/J2/J3/J4 + 雇用/解雇 + 反证）
- [ ] 每条引用有"为什么重要"的说明
- [ ] 每条引用可直接用于访谈/战略讨论/文案

### 使用建议
- [ ] 有访谈使用建议（如何用原话做情境还原）
- [ ] 有战略讨论建议（如何用数据锚定决策）
- [ ] 有文案使用建议（如何用用户句式做标题/卖点）

---

## 整体质量评估

### A 级标准（87.5+ 分）
- [ ] 数据采集：50+ 条真实引用，覆盖 5+ 平台，每条有 URL
- [ ] 框架应用：四力 + Job + Workaround 都到位，每个有 ≥5 条支撑
- [ ] 洞察质量：识别出核心差异化、关键场景、设计约束、情感价值
- [ ] 可执行性：可直接用于访谈准备 + 产品决策

### B+ 级标准（75-87 分）
- [ ] 数据采集：30-50 条引用，覆盖 3-4 平台
- [ ] 框架应用：四力 + Job 到位，Workaround 部分完整
- [ ] 洞察质量：有核心洞察但需补强
- [ ] 可执行性：可用于访谈准备，但产品决策需补充数据

### C 级标准（60-75 分）
- [ ] 数据采集：15-30 条引用，覆盖 2-3 平台
- [ ] 框架应用：四力或 Job 有缺失
- [ ] 洞察质量：有方向但不够深
- [ ] 可执行性：只能作为探索性研究

## 常见问题与改进建议

### 问题 1：数据量不足
**症状**：引用数 < 30 条
**改进**：
- 扩大搜索关键词范围
- 增加数据源平台
- 延长采集时间（再投入 1-2 天）

### 问题 2：缺少雇用/解雇时刻
**症状**：没有完整的切换时间线
**改进**：
- 在访谈中重点追问："你是什么时候第一次想到要买/做这个的？那天发生了什么？"
- 在访谈中追问："从想法到真正动手，中间隔了多久？为什么那天决定行动？"

### 问题 3：Job Story 格式不标准
**症状**：Job Story 更像功能描述，不是 Job Story
**改进**：
- 用标准格式重写：When [situation], I want to [motivation], so I can [outcome]
- 确保 situation 是具体场景（不是泛泛的"当我需要时"）
- 确保 outcome 是进展/结果（不是功能）

### 问题 3.5：Job Statement 被写成产品功能
**症状**：`Main Job` 写成“需要大空间/智能识别/自动提醒”，`Compensation Behavior` 写成“希望产品能...”
**改进**：
- 回到原始引用，重写 `Context` 和 `Main Job`：用户在什么具体情境下想完成什么动作？
- 把功能词移出 Job Statement，只作为下游 solution candidate。
- 缺少已发生 workaround 时，标 `缺证据`，并把它交给访谈追问。

### 问题 4：反证样本不足
**症状**：反证样本 < 15%
**改进**：
- 主动搜索"不需要这个的家庭"
- 主动搜索"试过但放弃的"
- 主动搜索"觉得现有方案就够的"

### 问题 5：缺少核心洞察
**症状**：分析报告只是数据堆砌，没有"啊哈时刻"
**改进**：
- 问自己：什么词/短语反复出现？（如"at a glance"）
- 问自己：所有失败方案的共同点是什么？
- 问自己：用户真正想要的是什么？（不是他们说的功能，而是背后的 Job）

## Bob Moesta 的金句提醒

1. **"People don't buy products, they hire them to make progress."**
   - 不要问"他们想要什么功能"，问"他们想要取得什么进展"

2. **"The job is not the product, the job is the progress."**
   - Job 不是产品，Job 是进展

3. **"You need at least 30-50 interviews to see patterns."**
   - 桌面研究可以先做 50+ 条引用，但最终需要 30-50 个访谈来验证

4. **"The moment of struggle is the moment of opportunity."**
   - 雇用时刻往往发生在"挣扎时刻"（某个痛苦事件触发）

5. **"Anxiety and Habit are the silent killers of innovation."**
   - 即使 Push 和 Pull 很强，Anxiety 和 Habit 也可能杀死创新

- 在 Phase 0 完成后，用本清单检查执行计划
- 在 Phase 1-5 完成后，用本清单检查每个 Phase 的产出
- 在 Phase 6 完成后，用"整体质量评估"给自己打分
- 如果 < B+ 级，按"常见问题与改进建议"补强
